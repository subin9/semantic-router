In the labyrinth, Ariadne's thread is what lets you find the way back. A routed request needs the same thing: when an answer comes from a pool of models, a set of policies and a long agent session, someone has to be able to follow the path it took and say whether that path was a good one.

[Hermes (v0.4)](/blog/v0.4-vllm-sr-hermes-release) gave an application one stable model name over many models. **Ariadne makes the judgment behind that name one model, one API and one configuration**, and follows the request from the first question the Router asks to the last tool call of an agent run.

**1,243 commits · 127 contributors · 80 first-time contributors** since Hermes. Thank you to everyone who built it.

<!-- truncate -->

## Ariadne in four moves

- **One model answers every judgment.** The System One decision model answers the routing signals, the model selector, the guards and the judges, through one API of typed questions. Vela 3.0 vela3-fast is the default, and it runs on a CPU.
- **A smaller stack.** The Router serves the OpenAI-compatible API itself, and a built-in model runtime serves every model the Router asks. Envoy is still available, but no longer required.
- **Agents on one gateway.** `vllm-sr connect` points Claude Code, Codex, Pi, OpenCode and VS Code at the Router, with the harness's own login where you want it, and Replay shows each agent run as one tree.
- **Evidence for every route.** A routing record is kept by default without prompt text, Shadow Dispatch compares several candidates under a budget, and recipe-lab ties a recipe change to a measured sr-bench result.

Ariadne is a breaking release. Read [Upgrade from v0.4](#upgrade-from-v04) before you move a production configuration.

## The decision model is first-class

The Router already answered most routing questions with one family of models, the System One decision models. Its configuration still described an older system, in which each signal had its own small specialist classifier or an embedding-similarity trick. Ariadne finishes that transition.

```json title="POST /v1/systemone"
{
  "state": {"request": "Prove that the square root of 2 is irrational."},
  "questions": {
    "math": {"type": "noul", "instructions": "Is this a mathematics request?"},
    "difficulty": {"type": "score", "instructions": "How hard is this request?",
                   "levels": ["Easy", "Medium", "Hard"]}
  }
}
```

A [System One](/docs/system-one/overview) question works as soon as you write it. There is no classifier to train and no example bank to collect. A rule in the configuration matches on the probabilities the model returns.

| What changed | In Ariadne |
| --- | --- |
| **Signals** | Three layers: the `systemone` primitive for questions you write, eleven application signals that each compile into one `systemone` question, and eight deterministic heuristic signals. |
| **Question types** | `choice`, `noul` (yes/no), `score`, `set` and `span`. A configuration fails to load when a question resolves to a model that cannot answer its type. |
| **Similarity** | One `match` block, with an optional embedding or BM25 `recall` stage and an optional System One `judge` stage with a hard cap on its candidates. Embeddings serve recall only and start lazily. |
| **Algorithms** | Selectors and executors. `escalate` replaces the Looper `confidence` algorithm and the native `cascade`. |
| **Plugins** | Plugins only act, on the signals they name. A response guard that can block or change an answer reads all of a streamed answer before it releases it. |
| **Configuration** | One structure at schema `v0.5`: defaults in `global`, routing in flat `recipes`, model facts on `providers.models[]`. |
| **Upstream auth** | Every upstream takes one `auth` block: a static key, the requesting user's delegated credential, or none. |

The [default decision model](/docs/system-one/overview#the-default-decision-model) is Vela 3.0 **vela3-fast**, a CPU-friendly encoder that answers every built-in question with trained adapters and calibrated thresholds and returns spans. Point `global.model_catalog.system.decision_model` at another deployment to change the model every question asks, or name a model on one signal, recipe or rule. A remote System One API can also serve as the decision model.

### Three generations of decision models

The models behind System One grew from one family into a ladder you can [choose from](/docs/model-runtime/get-started/choose-a-model):

| Family | Sizes | Answers |
| --- | --- | --- |
| [Vela 3.0 and 3.1](/blog/vela-3-0-name-it-vela-finds-it) | vela3-fast, lite 0.8B, mini 4B, flash 9B, turbo 27B; Vela 3.1 fast and pico | choice, noul and span; the larger sizes also score and read images |
| [Decision 3.0](/docs/model-runtime/supported-models/decision-3/overview) | edge 0.6B up to 27B, with d3-turbo and d3-ultra | choice, noul and score, over text, images and video |
| [Vela 2.0](/blog/vela-2-0-open-foundation-routing-models) | 0.3B, 0.8B, 4B, 9B | choice, noul, score, set and span |
| [Decision 2.0](/docs/model-runtime/supported-models/decision-2/overview) and 1.0 | Kai 0.6B up to Vega 27B | choice, noul and score |

[System One Auto](/blog/system-one-auto) routes the decision itself: a small decision model answers first, and a larger one takes the requests that fail the configured gate. In Ariadne it reads sets and spans as well as answers, and accepts a set by its least certain label.

## A smaller stack

### The Router serves the API itself

`vllm-sr serve` now starts [standalone mode](/docs/installation/gateway-modes) by default. The Router container publishes the configuration's `listeners`, answers `/health` and `/ready`, and proxies to the model backends. The routing decisions, the upstream requests and the responses are the same as behind Envoy. `vllm-sr serve --gateway extproc` keeps the previous Envoy stack for features the standalone Router does not have yet, such as token-bucket rate limiting, mTLS, JWT or OIDC.

The standalone gateway also drains in-flight requests on shutdown, trusts a private CA for HTTPS backends, mounts a listener's API under a path prefix, and checks entrypoint client keys before a request does any work.

### The built-in model runtime

Every model the Router uses now runs in the [built-in model runtime](/docs/model-runtime/overview), `vllm-srun`, which ships in every Router image. The in-process native bindings (Candle, ONNX Runtime and OpenVINO) are gone. A feature that never named a back end gets the same Vela model as before.

- **Engine mode** serves a decision model on its own: `vllm-sr serve vllm-sr/vela3.1-fast --engine --platform cpu` answers `POST /v1/systemone` with routing disabled.
- **Engine arguments** in the vLLM style replace the old numerics profiles. Lanes, packed forwards, cross-request batching, content caches and captured graphs keep small-model work off the request's critical path.
- **Quantized packages.** Decision 3.0 loads FP8, INT4 and NVFP4 packages.
- **Hardware.** CPUs work out of the box, with native BF16 where the CPU computes it and AMD zentorch kernels. AMD Instinct MI300X and MI325X and NVIDIA GPUs are validated. [Ascend NPUs](/docs/installation/ascend-npu) work and are not yet validated, and the standalone Router builds natively on [RISC-V64](/docs/installation/riscv64).

## Agents on one gateway

A coding agent sends hundreds of model calls in one task: the main loop, subagents, compactions, title threads and approval reviews. Ariadne treats that run as one thing to route, protect, budget and read.

### Connect a harness in one command

[`vllm-sr connect`](/docs/installation/agent-harness) writes the harness side of the connection and checks the rest:

```bash
vllm-sr connect claude-code
vllm-sr connect codex
vllm-sr connect pi
```

It finds the gateway at the first listener of your configuration, sets the harness's model aliases so subagents reach an entrypoint, and gives the harness the context window of the models behind it. `vllm-sr connect status` shows what it manages and whether it still holds. It can launch a harness in a new worktree, fetch the listener key with a command, connect the Codex app, and let Claude Code and Codex hand tasks to each other. OpenCode connects through its provider settings, and a VS Code extension serves the gateway's models in the editor.

A provider backend can also take the client's own provider login, so Claude Code on a Claude login or Codex on a ChatGPT login can route through the gateway and share a pool with keyed and local models.

### Know which agent sent the call

The [agent signal](/docs/tutorials/signal/heuristic/agent) identifies Claude Code, Codex, OpenCode, Cursor, OpenClaw and DeepSeek Harness requests and their subagents, and gives Claude Code, Codex, OpenCode and OpenClaw calls a request class (main, subagent, workflow, compaction or auxiliary), with no identity configuration. A recipe can route or block by agent and request class, for example sending compactions and session titles to a small model. Protection holds each subagent on its own model, and a route can escalate when an agent's tool calls keep failing.

### Bound the run

[Spend budgets](/docs/tutorials/global/api-and-observability#spend-budgets) apply per run and per user window, and Insights reports cost and savings with the provider's prompt-cache pricing and the Router's own model calls counted. The [vSR plugin](/blog/vsr-claude-code) brings the decision model into Claude Code and Codex CLI themselves: it guards, redacts and shields inside the harness, and can apply a listener's own rules.

### Read the run as one tree

Replay, traces and Insights show each agent run as one tree of sessions, turns, subagents and shared agent events, named by the session's title. The redesigned Requests page breaks traffic down by agent, model and decision, with cost in one currency, and shows a Timeline of each run.

## Evidence for every route

### Replay keeps a routing record by default

Router Replay now keeps a routing record by default, across restarts, and captures routing data only unless you choose a prompt capture mode. The prompt and request trace a record keeps are bounded. Tool results in Replay are opt-in for development and audit.

### Shadow Dispatch compares several candidates

[`router_replay.shadow`](/docs/tutorials/plugin/router-replay) sends a sampled copy of a request to several candidates and records one outcome per candidate. The candidates share a deadline, a concurrency limit, a response-byte budget, an estimated spend limit and a token bound. The live answer is never changed or delayed.

### recipe-lab closes the loop

recipe-lab attributes misroutes with a multi-signal oracle, proposes recipe changes against recorded traffic, and verifies a candidate through Preview and [sr-bench](/docs/benchmarking/sr-bench) before it reports a three-state verdict: pass, fail or inconclusive. A timed-out trial or missing guard evidence is inconclusive, never a pass. sr-bench stays the single source of evaluation results.

## Privacy and protocols

- **Masking.** The [masking plugin](/docs/tutorials/plugin/masking) replaces personal data before a provider reads it, keeps placeholders stable across requests and restarts, and can mask what a recipe's own rules find. It fails closed.
- **PII in tool results.** A route can act on personal data detected in tool output, not only in the user's text.
- **Speech.** `POST /v1/audio/speech` reaches vLLM-Omni TTS backends.
- **Responses.** Encrypted reasoning returns to the client and goes back only to an OpenAI-hosted model, so Codex on a ChatGPT login keeps its reasoning through a tool loop.
- **Recovery.** A call a backend never received is retried, allowlisted client headers ride fallback attempts, and the Router says when fallback is off.
- **Backends.** Ollama is verified as a backend, and the model catalog gained dozens of cards across open and hosted families.

## A Dashboard built around tasks

The Dashboard was rebuilt on a design system. A collapsible sidebar groups pages by job (Start, Routing, Models, Observe and Settings), a command menu opens with ⌘K, and light and dark themes follow the operating system. Built-in recipes publish from Mixture-of-Models, and the website gained a [use-case-first recipe page](/recipes) that lists each maintained recipe with its requirements and the commands that validate and serve it.

| **Evaluation & Quality** | Evaluate complete agent workflows | recipe-lab on sr-bench, and the agent routing protection baseline |

## Upgrade from v0.4

Ariadne is one breaking release, and a v0.4 configuration does not load unchanged.

1. Keep your original file and run `vllm-sr config migrate` once with the v0.5 CLI. It rewrites every form that maps and drops what v0.5 cannot execute, with a note on how to restore it.
2. Review the notes it prints, especially thresholds to re-fit, then validate the result.
3. Upgrade the Router and its model runtime together. The Router accepts only a model runtime from the same release.

A configuration that reads the client's identity (authz signals, per-user rate limits) needs `--gateway extproc`, or `listeners[].identity.trust_headers: true` behind an authenticating proxy. The [migration guide](/docs/installation/migrate-to-v0-5) lists every removed form, its load error and its rewrite.

```bash
pip install vllm-sr==0.5.0
vllm-sr config migrate --config config.yaml   # writes config.migrated.yaml
vllm-sr config validate --config config.migrated.yaml
vllm-sr serve --config config.migrated.yaml
```
